## 3. System Overview

`RingFallbackHook` is a Uniswap v4 `beforeSwap` hook for a current pool (cur pool) composed of origin tokens. Through `FewFactory`, it derives the corresponding FewToken wrappers and hookless fallback pool (fb pool).

The remediated design uses unified spot-price auto-routing with optional caller-supplied slippage limits:

1. The hook always compares cur and fb marginal `sqrtPriceX96` and routes to fb when strictly better. If fb is unavailable or not better, cur executes normally.
2. When fb is chosen with empty `hookData`, a post-execution safety check verifies fb's actual result against cur's marginal estimate. If fb underperforms, the transaction reverts.
3. When fb is chosen with non-empty `hookData` (`abi.encode(uint256 deadline, uint256 amountLimit)`), the caller's limit is enforced instead of the cur-marginal safety check — minimum output for exact-input, maximum input for exact-output.
4. `hookData` only controls slippage protection strength; it does not control routing. The hook always picks the better pool by spot price.
5. For fb, the hook derives the fallback key, performs strict 1:1 wrap/swap/unwrap conversion, and requires a complete fill.
6. It returns a `BeforeSwapDelta` that zeroes the cur swap only after a successful fb execution.
7. Invalid encoding, expiration, zero limit, insufficient inventory, partial fill, and limit violations revert when fb is chosen. Safety check failures also revert.

The hook no longer uses a fixed 10% estimate for exact-output inventory. Routing is always spot-price-based; `hookData` is optional and only provides stronger slippage protection.

The hook enables only `beforeSwap` and `beforeSwapReturnDelta`; its permission mask remains `0x88`. The contract has no owner, upgrade, pause, fee setter, route setter, or asset sweep capability.

## 6. Detailed Findings

### AI-H-01: Marginal Spot-Price Comparison Could Select the Worse Realized Route and Was MEV-Manipulable

**Severity:** High  
**Category:** Economic security / routing correctness / MEV  
**Original location:** audited-version routing and price-comparison logic  
**Status:** Resolved

#### Original Description

The original route selection compared only the two pools' pre-trade `sqrtPriceX96`. That value represented a marginal price but did not account for:

- trade size;
- each pool's liquidity depth and tick distribution;
- post-trade price impact;
- a complete executable quote; or
- a minimum improvement threshold for small differences and rounding.

An fb pool could therefore show a slightly better pre-trade marginal price but produce a worse final execution because it was shallower. Once the hook selected fb, `specifiedDelta = -amountSpecified` entirely replaced the cur trade, so the user could not automatically switch to the route with the better realized quote in the same transaction.

An attacker could also temporarily move the fb spot price before a user's trade, induce fb selection, and reverse the position after the user's price impact. `sqrtPriceLimitX96` constrained absolute slippage but did not prove that fb was better than cur. Avoidable losses could remain within the user's slippage tolerance.

#### Original Impact

- A user could receive less output than cur offered or pay more input for exact-output.
- Predictable large trades could be sandwiched or induced into a shallower fb pool.
- The claimed automatic "better price" routing property could not be guaranteed.

This was an execution-quality and economic risk constrained by the user's price limit, not a direct protocol- or LP-asset theft path.

#### Original Recommendation

Because `beforeSwap` runs during an unlocked PoolManager swap flow, the hook cannot simply perform and roll back two nested swaps to obtain side-effect-free route quotes. The primary recommendation was to compare complete quotes off chain, pass an explicit route selection, quote deadline, and minimum-output/maximum-input constraint through validated `hookData`, and remove any promise of automatic best execution.

#### Resolution

The implementation now uses a unified spot-price routing design at `src/RingFallbackHook.sol`:

- The hook **always** compares cur and fb marginal `sqrtPriceX96` and routes to fb when strictly better. There is no "explicit force fb" mode — routing is always price-based.
- When fb is chosen with empty `hookData`, a safety check verifies that fb's actual result beats cur's marginal estimate. If fb's actual output (exact-input) or input (exact-output) is worse than cur's marginal estimate, the transaction reverts. This catches shallow-pool traps where spot price is misleading.
- When fb is chosen with non-empty `hookData` (`abi.encode(deadline, amountLimit)`), the caller's limit is enforced instead of the cur-marginal safety check, providing full slippage protection.
- `hookData` only controls slippage protection strength; it does not control the routing decision.
- When fb is unavailable or not better, cur executes normally and `hookData` is ignored.

The safety check uses cur's marginal (best-case) output/input as the threshold. This is conservative: fb only executes when it beats cur's best-case scenario. The check may revert in edge cases where fb is competitive but does not exceed cur's marginal rate — in such cases, the user can retry with `hookData` containing a caller-supplied limit.

### AI-M-01: Fixed 10% Exact-Output Inventory Estimate Could Cause Incorrect Fallback or Reversion

**Severity:** Medium  
**Category:** Correctness / availability  
**Original location:** audited-version exact-output precheck and inventory logic  
**Status:** Resolved

#### Original Description

For `amountSpecified > 0` exact-output swaps, the original hook read the PoolManager's global origin-token ERC-20 balance and estimated required input as:

```solidity
requestedInput = exactOutput + exactOutput / 10;
```

That balance was not a pool-specific reserve or claim balance. More importantly, the fixed 10% addition did not use the route price, fees, ticks, token units, or actual `amountIn`, despite comments referring to a price-ratio estimate.

Two errors were possible:

1. **Underestimation:** the precheck passed, actual fb input exceeded available physical origin-token inventory, and a later take or transfer reverted instead of gracefully falling back to cur.
2. **Overestimation:** the precheck rejected fb even though PoolManager held enough origin input for the actual execution, causing incorrect route selection.

At the original audit point, integration and fork tests used exact-input and did not cover exact-output.

#### Original Impact

- Valid exact-output transactions could consistently fail.
- Transactions could incorrectly select cur.
- The claimed inventory-shortage graceful fallback was not reliable for exact-output.

#### Original Recommendation

The preferred remediation was for an off-chain quoter to provide a user-authorized exact-output maximum input and deadline through validated `hookData`, followed by checks against actual execution and actual inventory. Tests should cover exact-output in both directions, aligned and reversed token ordering, inventory boundaries, non-1:1 market prices, tick crossing, partial fills, and limit violations.

#### Resolution

The fixed 10% estimate has been removed. The caller now explicitly encodes maximum input as `amountLimit` for exact-output. The hook executes the selected fb route, obtains actual `amountIn`, rejects values above the authorized maximum at `src/RingFallbackHook.sol:146-150`, and checks PoolManager's actual origin-token inventory against that result at `src/RingFallbackHook.sol:152-156`.

Failure is atomic and explicit: maximum-input or inventory failure reverts the fb request; it does not redirect to cur. The external quoter remains responsible for deriving a suitable maximum input from a complete fb quote and comparing it with the cur quote.

### AI-L-01: `_pay` Ignores `payer`, Creating Potentially Incorrect Settlement Semantics

**Severity:** Low  
**Category:** Potential correctness / maintainability  
**Location:** `src/RingFallbackHook.sol:409-411`  
**Status:** Open

#### Description

`DeltaResolver._settle(currency, payer, amount)` semantically requires the implementation to pay from the specified `payer`, but the current `_pay` override ignores `payer` and always transfers from the hook's own balance:

```solidity
function _pay(Currency currency, address, uint256 amount) internal override {
    currency.transfer(address(poolManager), amount);
}
```

The current version uses custom `_settleExact` logic and does not call inherited `_settle`, so this issue is presently unreachable and does not directly affect the existing swap flow. If a future change reuses `DeltaResolver._settle`, however, the behavior would differ from the caller's expectation and could fail settlement or incorrectly consume hook balances.

#### Recommendation

Choose one of the following:

- correctly implement `payer` semantics by paying PoolManager from `payer` for supported token types; or
- if inherited `_settle` will never be used, remove `DeltaResolver`, locally implement the currently required `_take` behavior, and retain explicit settlement logic and the `poolManager` state supplied by `BaseHook`.

Until then, keep this finding open and prevent future code from calling inherited `_settle` without resolving the semantic mismatch.

## 7. Trust Boundaries and Design Risks

### 7.1 FewFactory and Wrappers Are Critical Trusted Components

The hook verifies that a wrapper has code and that `token()` returns the expected underlying token. Security still depends on FewFactory mappings and wrapper implementations satisfying these assumptions:

- wrap/unwrap is strictly 1:1;
- no transfer tax, rebase, or additional burn/mint behavior exists;
- calls do not maliciously revert or reenter; and
- an untrusted party cannot upgrade or replace the implementation.

Return-value and balance-delta checks prevent some abnormal behavior, but a malicious or compromised factory/wrapper can still cause persistent denial of service for explicit fb requests. Because the hook has no pause or route override, a faulty wrapper cannot be isolated at the hook layer. Integrators can continue selecting cur with empty data or migrate to a new hook.

### 7.2 External Quoter and Router Are Recommended for Full Protection

The hook always uses marginal spot price as the routing signal with a cur-marginal safety check. This provides automatic fb selection when fb is better, but the safety check is conservative and may revert in edge cases. For full slippage protection, a production integration should quote both routes for the full intended amount off chain and encode a caller-supplied limit in `hookData`.

When `hookData` is provided, the integration must encode a short deadline and nonzero minimum output or maximum input. When `hookData` is empty and fb is chosen, the cur-marginal safety check applies. When cur is chosen (fb not better or unavailable), the router and user must preserve normal safeguards such as `sqrtPriceLimitX96`, transaction deadlines, and router-level minimum-output/maximum-input constraints.

### 7.3 PoolManager Physical Inventory Dependency

The fb route takes origin input from PoolManager's global physical balance before wrapping, swapping, and unwrapping. Availability depends on PoolManager holding enough of the relevant origin asset at execution time. The current implementation checks the actual fb input against physical inventory. Insufficiency reverts the explicit fb request; there is no graceful switch to cur.

### 7.4 Non-Standard Token Incompatibility

Strict balance-equality checks mean fee-on-transfer, rebasing, transfer-hook, or other non-standard balance behavior may revert. The deployment should use an asset allowlist or clearly limit support to verified standard ERC-20 tokens and strict 1:1 FewToken wrappers.

### 7.5 No Administrative or Emergency Powers

The absence of owner, upgrade, pause, and sweep functions reduces administrative-key risk, but it also means:

- a compromised fallback route cannot be disabled in the hook;
- FewFactory problems cannot be patched locally;
- affected fb requests can only be avoided by selecting cur externally, or by deploying a new hook and migrating liquidity.

### 7.6 Explicitly Unsupported or Reverting Cases

- Non-empty `hookData` that is not exactly 64-byte `(uint256,uint256)` ABI encoding reverts when fb is chosen. When cur is chosen, `hookData` is ignored.
- fb routing requires ERC-20 currencies; the cur route retains standard v4 native-currency behavior, and WETH may be used for fb.
- Dynamic-fee pools retain standard behavior on the cur route but are unavailable for fb routing.
- The fb pool must be hookless and use the cur pool's fee and tick spacing.
- When fb is unavailable or not better by spot price, cur executes normally regardless of `hookData`.

## 10. Final Conclusion

The contract uses a clear least-privilege model: no administrative keys, a fixed `0x88` permission mask, strict 1:1 balance checks, complete fb fills, actual-result limits, and no intended residual hook balances.

The unified spot-price routing design mitigates `AI-H-01` by always comparing marginal spot prices and adding a cur-marginal safety check that catches shallow-pool traps. It resolves `AI-M-01` by removing the fixed 10% exact-output estimate in favor of actual-result checking. Optional `hookData` provides caller-supplied slippage protection when fb is chosen. `AI-L-01` remains open because `_pay` still ignores `payer`, although that path is currently unreachable.

Production readiness still depends on the safety check's conservative behavior being acceptable for the intended use case, or on integrators providing `hookData` with full off-chain quotes. The FewFactory/FewToken trust boundary, PoolManager inventory dependency, non-standard-token limitations, open low-severity finding, and test gaps should be addressed or explicitly accepted before deployment.
