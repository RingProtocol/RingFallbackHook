## 3. System Overview

`RingFallbackHook` is a Uniswap v4 `beforeSwap` hook for a current pool (cur pool) composed of origin tokens. Through `FewFactory`, it derives the corresponding FewToken wrappers and hookless fallback pool (fb pool).

The hook uses depth-based routing to the fb pool. The cur pool is never used as a fallback venue — all swaps must execute on fb, or the transaction reverts:

1. The hook derives the fb route (registered pool first, then FewFactory auto-inference). If no route is available, the swap reverts with `FbRouteUnavailable`.
2. The hook compares cur and fb active liquidity. If fb is not strictly deeper than cur, the swap reverts with `FbShallowerThanCur`. This ensures fb has sufficient depth.
3. Before executing the fb swap, the hook pre-checks PoolManager physical inventory (origin input and fewToken output). If insufficient, the swap reverts with `FbInsufficientInventory` to save gas.
4. The hook executes the fb swap with strict 1:1 wrap/swap/unwrap conversion and requires a complete fill. Partial fills revert with `FbSwapPartialFill`.
5. `hookData` is ignored — routing is purely depth-based and not controllable by the caller.
The hook enables only `beforeSwap` and `beforeSwapReturnDelta`; its permission mask remains `0x88`. The contract has a single transferable `owner` (set to the deployer at construction) that can register explicit fb pool mappings. There is no upgrade, fee setter, pause, or asset sweep capability.

## 6. Detailed Findings

### AI-H-01: Marginal Spot-Price Comparison Could Select the Worse Realized Route and Was MEV-Manipulable

**Severity:** High  
**Category:** Economic security / routing correctness / MEV  
**Original location:** audited-version routing and price-comparison logic  
**Status:** Superseded (depth-based fb-only routing replaces spot-price comparison)

#### Original Description

The original route selection compared only the two pools' pre-trade `sqrtPriceX96`. That value represented a marginal price but did not account for:

- trade size;
- each pool's liquidity depth and tick distribution;
- post-trade price impact;
- a complete executable quote; or
- a minimum improvement threshold for small differences and rounding.

An fb pool could therefore show a slightly better pre-trade marginal price but produce a worse final execution because it was shallower. Once the hook selected fb, `specifiedDelta = -amountSpecified` entirely replaced the cur trade, so the user could not automatically switch to the route with the better realized quote in the same transaction.

An attacker could also temporarily move the fb spot price before a user's trade, induce fb selection, and reverse the position after the user's price impact. `sqrtPriceLimitX96` constrained absolute slippage but did not prove that fb was better than cur. Avoidable losses could remain within the user's slippage tolerance.

#### Original Impact

- A user could receive less output than cur offered or pay more input for exact-output.
- Predictable large trades could be sandwiched or induced into a shallower fb pool.
- The claimed automatic "better price" routing property could not be guaranteed.

This was an execution-quality and economic risk constrained by the user's price limit, not a direct protocol- or LP-asset theft path.

#### Original Recommendation

Because `beforeSwap` runs during an unlocked PoolManager swap flow, the hook cannot simply perform and roll back two nested swaps to obtain side-effect-free route quotes. The primary recommendation was to compare complete quotes off chain, pass an explicit route selection, quote deadline, and minimum-output/maximum-input constraint through validated `hookData`, and remove any promise of automatic best execution.

#### Resolution

The implementation now uses a unified spot-price routing design at `src/RingFallbackHook.sol`:

- The hook compares cur and fb active liquidity and routes to fb only when fb is strictly deeper. If fb is not deeper, the swap reverts with `FbShallowerThanCur`.
- The hook pre-checks PoolManager physical inventory before executing the fb swap. If insufficient, the swap reverts with `FbInsufficientInventory`.
- `hookData` is ignored — routing is purely depth-based and not controllable by the caller.
- When fb is unavailable, not deeper, or has insufficient inventory, the swap reverts. The cur pool is never used as a fallback venue.

The depth-based routing ensures fb has sufficient liquidity to handle the swap. The pre-check saves gas by reverting before the fb swap executes when PoolManager lacks the physical inventory for the flash-take/settle cycle.

### AI-M-01: Fixed 10% Exact-Output Inventory Estimate Could Cause Incorrect Fallback or Reversion

**Severity:** Medium  
**Category:** Correctness / availability  
**Original location:** audited-version exact-output precheck and inventory logic  
**Status:** Resolved (inventory pre-check and actual-result checking)

#### Original Description

For `amountSpecified > 0` exact-output swaps, the original hook read the PoolManager's global origin-token ERC-20 balance and estimated required input as:

```solidity
requestedInput = exactOutput + exactOutput / 10;
```

That balance was not a pool-specific reserve or claim balance. More importantly, the fixed 10% addition did not use the route price, fees, ticks, token units, or actual `amountIn`, despite comments referring to a price-ratio estimate.

Two errors were possible:

1. **Underestimation:** the precheck passed, actual fb input exceeded available physical origin-token inventory, and a later take or transfer reverted instead of gracefully falling back to cur.
2. **Overestimation:** the precheck rejected fb even though PoolManager held enough origin input for the actual execution, causing incorrect route selection.

At the original audit point, integration and fork tests used exact-input and did not cover exact-output.

#### Original Impact

- Valid exact-output transactions could consistently fail.
- Transactions could incorrectly select cur.
- The claimed inventory-shortage graceful fallback was not reliable for exact-output.

#### Original Recommendation

The preferred remediation was for an off-chain quoter to provide a user-authorized exact-output maximum input and deadline through validated `hookData`, followed by checks against actual execution and actual inventory. Tests should cover exact-output in both directions, aligned and reversed token ordering, inventory boundaries, non-1:1 market prices, tick crossing, partial fills, and limit violations.

#### Resolution

The fixed 10% estimate has been removed. The hook now pre-checks PoolManager's physical inventory before executing the fb swap. For exact-input, it checks the origin input balance directly. For exact-output, it estimates the marginal `amountIn` from the fb pool's `sqrtPriceX96` using `FullMath.mulDiv` and checks against the origin input balance. If insufficient, the swap reverts with `FbInsufficientInventory` before executing the fb swap, saving gas. A post-swap safety-net check also reverts with `InsufficientSettlementInventory` if the exact-output marginal estimate was too low.

Failure is atomic and explicit: inventory failure reverts the transaction; it does not redirect to cur. The cur pool is never used as a fallback venue.

### AI-L-01: `_pay` Ignores `payer`, Creating Potentially Incorrect Settlement Semantics

**Severity:** Low  
**Category:** Potential correctness / maintainability  
**Location:** `src/RingFallbackHook.sol:409-411`  
**Status:** Open

#### Description

`DeltaResolver._settle(currency, payer, amount)` semantically requires the implementation to pay from the specified `payer`, but the current `_pay` override ignores `payer` and always transfers from the hook's own balance:

```solidity
function _pay(Currency currency, address, uint256 amount) internal override {
    currency.transfer(address(poolManager), amount);
}
```

The current version uses custom `_settleExact` logic and does not call inherited `_settle`, so this issue is presently unreachable and does not directly affect the existing swap flow. If a future change reuses `DeltaResolver._settle`, however, the behavior would differ from the caller's expectation and could fail settlement or incorrectly consume hook balances.

#### Recommendation

Choose one of the following:

- correctly implement `payer` semantics by paying PoolManager from `payer` for supported token types; or
- if inherited `_settle` will never be used, remove `DeltaResolver`, locally implement the currently required `_take` behavior, and retain explicit settlement logic and the `poolManager` state supplied by `BaseHook`.

Until then, keep this finding open and prevent future code from calling inherited `_settle` without resolving the semantic mismatch.

## 7. Trust Boundaries and Design Risks

### 7.1 FewFactory and Wrappers Are Critical Trusted Components

The hook verifies that a wrapper has code and that `token()` returns the expected underlying token. Security still depends on FewFactory mappings and wrapper implementations satisfying these assumptions:

- wrap/unwrap is strictly 1:1;
- no transfer tax, rebase, or additional burn/mint behavior exists;
- calls do not maliciously revert or reenter; and
- an untrusted party cannot upgrade or replace the implementation.

Return-value and balance-delta checks prevent some abnormal behavior, but a malicious or compromised factory/wrapper can still cause persistent denial of service. The owner can register an alternative fb pool (`setFbPool`) to bypass the compromised factory. Integrators can also migrate to a new hook.

### 7.2 External Quoter and Router Are Recommended for Full Protection

The hook uses depth-based routing to fb and requires fb to be strictly deeper than cur. Slippage protection is provided by `sqrtPriceLimitX96` (mapped to fb's price space) and the caller's router deadline/amount limits. For full slippage protection, a production integration should quote the fb route for the full intended amount off chain and set appropriate router-level minimum-output/maximum-input constraints.

The hook ignores `hookData` — routing is not controllable by the caller. The router and user must preserve normal safeguards such as `sqrtPriceLimitX96`, transaction deadlines, and router-level minimum-output/maximum-input constraints.

### 7.3 PoolManager Physical Inventory Dependency

The fb route takes origin input from PoolManager's global physical balance before wrapping, swapping, and unwrapping. Availability depends on PoolManager holding enough of the relevant origin asset at execution time. The hook pre-checks physical inventory before executing the fb swap and reverts with `FbInsufficientInventory` if insufficient. A post-swap safety-net check also reverts with `InsufficientSettlementInventory` if the exact-output marginal estimate was too low. There is no graceful switch to cur — the swap always reverts when fb cannot be serviced.

### 7.4 Non-Standard Token Incompatibility

Strict balance-equality checks mean fee-on-transfer, rebasing, transfer-hook, or other non-standard balance behavior may revert. The deployment should use an asset allowlist or clearly limit support to verified standard ERC-20 tokens and strict 1:1 FewToken wrappers.

### 7.5 Administrative Powers: Owner and fb Pool Registration

The contract has a single transferable `owner` (set to the deployer at construction) with two capabilities:

- `transferOwner`: transfers ownership to a new address (zero address rejected).
- `setFbPool` / `removeFbPool`: registers or removes an explicit fb pool definition (few0, few1, fee, tickSpacing) keyed by the origin currency pair. Registered pools take precedence over FewFactory auto-inference; when no registration exists, the hook falls back to deriving the fb pool from the cur pool key and FewFactory state.

Risks and mitigations:

- The owner key becomes a trust boundary. A compromised owner can redirect fb pools to attacker-controlled wrappers. Mitigate with multisig/timelock ownership and careful key management. There is no two-step ownership acceptance; `transferOwner` takes effect immediately.
- Registered fb pools are still validated at swap time: wrappers must have code and `token()` must return the expected underlying (WETH for native ETH). A registered pool whose wrappers are later compromised or removed from FewFactory will fail validation and the swap reverts with `FbRouteUnavailable` rather than executing against invalid wrappers.
- The fb pool map key is `keccak256(abi.encodePacked(origin0, origin1))` with `origin0 < origin1` enforced, so registrations are deterministic per origin pair. The key does not include fee or tick spacing, so a single registration overrides all cur pools sharing that origin pair regardless of their fee/tick spacing. Register per pair only when this is intended.
- There is no upgrade, fee setter, pause, or asset sweep capability. The owner cannot move funds, change the cur pool, or alter the permission mask.

### 7.6 Explicitly Unsupported or Reverting Cases

- `hookData` is ignored by the hook. Routing is purely depth-based and not controllable by the caller.
- fb routing requires ERC-20 currencies; native ETH is supported via WETH bridging. Dynamic-fee pools are unavailable for fb routing (the swap reverts).
- The fb pool must be hookless. Registered fb pools may use different fee/tick spacing from the cur pool; auto-inferred fb pools reuse the cur pool's fee and tick spacing.
- When fb is unavailable, not deeper than cur, or has insufficient inventory, the swap reverts. The cur pool is never used as a fallback venue.

## 10. Final Conclusion

The contract uses a clear least-privilege model: a single transferable `owner` for administrative functions, a fixed `0x88` permission mask, strict 1:1 balance checks, complete fb fills, and no intended residual hook balances. The cur pool is never used as a fallback venue — all swaps must execute on fb, or the transaction reverts.

The depth-based fb-only routing design supersedes `AI-H-01` by eliminating spot-price comparison and cur fallback entirely. fb is used only when strictly deeper than cur; otherwise the swap reverts. It resolves `AI-M-01` by replacing the fixed 10% estimate with a marginal-price inventory pre-check and actual-result checking. `AI-L-01` remains open because `_pay` still ignores `payer`, although that path is currently unreachable.

Production readiness depends on the fb-only design being acceptable for the intended use case: when fb is unavailable, shallower, or has insufficient inventory, swaps revert rather than falling back to cur. The FewFactory/FewToken trust boundary, PoolManager inventory dependency, non-standard-token limitations, owner centralization, open low-severity finding, and test gaps should be addressed or explicitly accepted before deployment.
